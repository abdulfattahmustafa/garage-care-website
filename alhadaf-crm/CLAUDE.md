# CLAUDE.md — alhadaf-crm

نظام إدارة علاقات عملاء (CRM) **متعدد المعارض (multi-tenant)** لمعارض السيارات. بُني أصلًا تلبيةً لبرومبت `CRM_PROMPT.md` لمعرض واحد ("الهدف الأميز"، جدة، KSA) ومرتبط بمتطلبات معيار "إدارة علاقات العملاء" (10%) ضمن برنامج جميل بلس 2026 من عبداللطيف جميل موتورز، ثم تحوّل بطلب صريح من المالك إلى منتج SaaS يقدر أي معرض سيارات ثاني يشترك فيه، ببيانات معزولة بالكامل عن بقية المعارض. راجع قسم "البنية متعددة المعارض" بالأسفل قبل أي تعديل — أي route جديد أو جدول جديد لازم يمشي على نفس النمط (`req.db`، مو اتصال عام).

## التقنيات المستخدمة ولماذا

- **Node.js + Express**: خادم بسيط، أمر تشغيل واحد (`npm start`)، بدون خطوات بناء (build) معقدة — مناسب لمستخدم غير مبرمج.
- **node:sqlite (المدمجة في Node.js، وليست `better-sqlite3`)**: قاعدة بيانات حقيقية بملف مستقل لكل معرض (`data/tenants/<slug>/data.db`)، متزامنة (synchronous API يبسّط الكود). **تجنّبنا `better-sqlite3` عمدًا**: أول نسخة استخدمتها فشلت عند المالك (نسخة Node.js حديثة جدًا 24.18.0 على ويندوز بدون prebuilt binaries، فاضطر npm للبناء من المصدر عبر node-gyp، وفشل لعدم وجود Python/Visual Studio Build Tools). التبديل لـ `node:sqlite` (متوفرة افتراضيًا من Node 22.5+ بدون أي flag) ألغى الحاجة لأي تجميع أصلي (native compile) نهائيًا. الفرق الوحيد في الكود: `db.exec('PRAGMA ...')` بدل `db.pragma(...)`, والمعاملات (transactions) تُكتب يدويًا بـ `BEGIN/COMMIT/ROLLBACK` بدل `db.transaction()`.
- **EJS**: قوالب HTML بسيطة تُصيَّر من السيرفر (server-rendered)، تدعم RTL والعربي بدون تعقيد أدوات بناء frontend حديثة.
- **express-session**: جلسة بكوكي، تخزّن `userId`/`userName` بعد نظام الحسابات المتعددة (كانت `authed: true` بس بمرحلة كلمة المرور المشتركة الأولى).
- **bcryptjs** (وليس `bcrypt`): تشفير كلمات المرور، نسخة JS بحتة بدون أي تجميع أصلي — نفس فلسفة تفادي `better-sqlite3` بالأسفل.
- **multer v2** (وليس v1، فيها ثغرات معروفة): رفع المرفقات (`server/lib/upload.js`) بقائمة أنواع مسموحة (JPG/PNG/WEBP/PDF فقط) وأسماء ملفات عشوائية على القرص.
- **json2csv**: تصدير Excel/CSV بدون مكتبات ثقيلة.
- **Chart.js** (مُوَرَّد محليًا في `public/js/chart.umd.min.js`، بدون CDN): رسوم بيانية في اللوحة الرئيسية.
- **خط Tajawal** مُنزَّل محليًا في `public/fonts/` (وليس عبر Google Fonts CDN) — درس مستفاد من مشروع سابق (`CLAUDE_CODE_HANDOFF.md`) أن خطوط النظام لا تشكّل العربي بشكل موثوق.

## البنية متعددة المعارض (multi-tenant)

**القرار المعماري**: عزل بيانات كل معرض عبر **قاعدة بيانات SQLite منفصلة بالكامل لكل معرض** (database-per-tenant)، وليس جدول واحد مشترك بعمود `tenant_id`. هذا قرار متعمد اتخذناه بعد طلب صريح من المالك بجعل عزل البيانات "أول وأهم شيء" قبل أي شيء آخر: مع عمود `tenant_id` مشترك، أي استعلام ينسى شرط `WHERE tenant_id=?` (خطأ بشري سهل الحدوث) يسرّب بيانات معرض لمعرض ثاني بصمت بدون أي خطأ ظاهر. مع قاعدة بيانات منفصلة لكل معرض، هذا النوع من التسريب **مستحيل بنيويًا** — ما فيه جدول مشترك أصلاً يمكن ينسى فلترته.

- **`data/registry.db`**: قاعدة بيانات صغيرة مشتركة، فيها جدول `tenants` واحد بس (`slug` فريد، `name`، `is_active`) — يُستخدم فقط عند تسجيل الدخول/التسجيل للتحقق "هل رمز المعرض هذا موجود ومفعّل؟" قبل أي وصول لبيانات المعرض الفعلية.
- **`data/tenants/<slug>/data.db`**: قاعدة بيانات كاملة مستقلة لكل معرض (كل الجداول: customers, prospects, car_inventory, users, activity_log...)، تُنشأ تلقائيًا (`initSchema`) أول مرة يُفتح فيها اتصال لهذا المعرض. `server/tenantDb.js` يحتفظ باتصال واحد مفتوح لكل معرض طول عمر العملية (`dbCache`، خريطة `slug → DatabaseSync`).
- **`data/tenants/<slug>/uploads/`**: مجلد مرفقات منفصل لكل معرض، محدَّد عبر `tenantDb.getUploadsDir(slug)`.
- **middleware تحديد قاعدة البيانات** (`server/index.js`، بعد `requireAuth`): `req.db = tenantDb.getTenantDb(req.session.tenantSlug)` يشتغل قبل كل route محمي، فكل route handler يستخدم `req.db` بدل أي اتصال عام مستورد على مستوى الملف. **هذا هو النمط الإلزامي لأي route جديد** — لا تكتب `const db = require('../db')` أبدًا (هذا الملف محذوف عمدًا)، ولا `tenantDb.getTenantDb(...)` مباشرة داخل route (يفوّت التحقق من الجلسة).
- **تسجيل الدخول** (`POST /login`) يطلب 3 حقول: رمز المعرض + اسم المستخدم + كلمة المرور. رسالة الخطأ عامة ("رمز المعرض أو اسم المستخدم أو كلمة المرور غير صحيح") لكل الحالات الثلاث عمدًا، حتى ما يقدر أي شخص يكتشف أي رموز معارض موجودة فعليًا بمجرد تجربة أسماء (enumeration).
- **التسجيل** (`POST /signup`) يُنشئ صف جديد بـ `registry.db` + قاعدة بيانات جديدة كاملة بالسكيمة + أول حساب مستخدم (مدير) — كل هذا في `tenantDb.createTenant(slug, name)`.
- **الترحيل التلقائي من النسخة الأحادية القديمة**: `migrateLegacySingleTenantIfNeeded()` في `index.js` يتحقق عند بدء التشغيل هل فيه `data/alhadaf.db` قديم (من قبل هذا التحديث) وما فيه أي معرض مسجّل بعد — لو نعم، ينسخه تلقائيًا كأول معرض برمز `alhadaf` بدل ما يتيتم البيانات الحقيقية. يشتغل مرة وحدة بس (بعدها `listTenants().length > 0` يمنع إعادة التنفيذ).
- **`server/lib/schema.js`** هو المصدر الوحيد لتعريف الجداول — أي عمود/جدول جديد يُضاف هنا (بنفس منطق الهجرات الآمنة الموصوف بالأسفل)، ويتطبّق تلقائيًا على أي معرض (قديم أو جديد) أول مرة تُفتح قاعدة بياناته بعد التحديث.
- **العلامة التجارية ديناميكية**: `res.locals.tenantName` (من `req.session.tenantName`) يُستخدم بدل أي اسم معرض مكتوب يدويًا في القوالب (`nav.ejs`, `head.ejs`) وفي نصوص التصدير/الواتساب (`dashboard.js`, `data.js`, `customers/detail.ejs`) — لا تكتب اسم معرض ثابت بالكود أبدًا.
- **اختُبرت العزلة يدويًا وبشكل صارم** قبل الدمج: أُنشئ معرضان تجريبيان بحسابين منفصلين، وأُضيفت بيانات مميزة لكل واحد (عميل، عميل محتمل، بائع، سيارة كتالوج، مرفق) عبر curl مع ملفات cookies منفصلة — تم التحقق أن كل معرض يشوف بياناته فقط في: قائمة العملاء، `/customers/:id` (حتى لو نفس الرقم التسلسلي متطابق بين المعرضين لأنهما قاعدتا بيانات منفصلتان)، `backup.json`، العملاء المحتملين، كتالوج السيارات، قائمة البائعين، سجل النشاط، ومجلد المرفقات على القرص. كذلك تأكدنا أن تسجيل الدخول برمز معرض A مع بيانات حساب من معرض B يُرفض.

## نموذج البيانات (customers)

الحقول الإلزامية: `customer_name, national_id (10 أرقام), sale_date, payment_method, car_type, vin (17 خانة فريد), estimara_number (فريد)`.
حقول إضافية: `phone (05xxxxxxxx), salesperson, price, notes, status, delivery_at, car_inventory_id`.
حقول تتبّع: `reported/reported_at` (تبليغ المبيعات), `followup_done/followup_result/followup_note/followup_at` (متابعة ما بعد البيع), `created_by/updated_by` (اسم المستخدم، نص حر مو FK — يبقى بالسجل حتى لو انحذف الحساب), `is_demo` (لتمييز بيانات التجربة).

## جداول إضافية

- **`users`**: `name, username (فريد ضمن نفس المعرض بس — نفس اسم المستخدم يقدر يتكرر بمعرض ثاني لأنه جدول مستقل), password_hash (bcryptjs), is_active`. أول حساب لكل معرض يُنشأ عبر `POST /signup` (مو تلقائيًا من `.env`) — بعد كذا كل التحكم بالحسابات من `/users`.
- **`activity_log`**: `user_name, action, entity_type, entity_id, details, created_at`. تُملأ عبر `logActivity(req, action, {...})` (`server/lib/activity.js`) — مُستدعاة من كل مسار يعدّل بيانات (customers/prospects/cars/settings/sop/users). `user_name` نص حر (مو FK) لنفس سبب `created_by` أعلاه.
- **`prospects`** + **`prospect_log`**: نفس بنية `customers`/`contact_log` تقريبًا بس للعملاء المحتملين (قبل البيع). حقل `stage` (قائمة ثابتة في `prospects.js`: جديد/تواصل أولي/زار المعرض/تجربة قيادة/تفاوض على السعر/لم يتم البيع/تحوّل لعميل) و`converted_customer_id` (FK لـ customers، `ON DELETE SET NULL`).
- **`attachments`**: `customer_id (FK CASCADE), label, original_name, stored_name (عشوائي على القرص، فريد), mime_type, size, uploaded_by`. الملفات تُحفظ فعليًا في `<dataDir>/tenants/<slug>/uploads/` (خارج مجلد المشروع لو `DATA_DIR` مضبوط) — **غير مشمولة إطلاقًا في نسخة JSON الاحتياطية**، لازم تُنسخ يدويًا لو احتجت نسخ احتياطي كامل للمرفقات.

`car_type` يبقى نص حر مركّب (مثال: `Toyota Camry 2026 - أبيض`) — ده اللي يُستخدم في البحث/الفلترة/التصدير كما هو. `car_inventory_id` مرجع اختياري (FK، `ON DELETE SET NULL`) لجدول `car_inventory` يُملأ تلقائيًا لو العميل اختار السيارة من قائمة الكتالوج بدل الكتابة اليدوية، ويُستخدم مستقبلًا لو احتجنا نحسب هامش الربح (سعر البيع - سعر الشراء). حذف سيارة من الكتالوج يفرّغ `car_inventory_id` فقط في السجلات القديمة (`ON DELETE SET NULL`) — نص `car_type` يبقى كما هو دائمًا، فالسجل التاريخي ما يتأثر.

جدول `contact_log` منفصل (علاقة واحد-لمتعدد مع customers) لتسجيل كل مكالمة/زيارة/رسالة — هذا يغطي متطلب "العمليات والإجراءات" الموثقة رسميًا في معيار CRM.

## منطق التذكيرات (server/lib/util.js)

- **تذكير المتابعة**: `delivery_at + 24 ساعة`، يظهر في لوحة "مستحقات اليوم" ما دام `followup_done = 0`.
- **موعد تبليغ المبيعات**: نهاية الشهر التالي لشهر `sale_date` (مثال: بيع في يونيو → الموعد 31 يوليو). يتحول لونه أحمر (متأخر) لو فات الموعد ولم يُبلَّغ، وأصفر لو باقي أسبوع أو أقل.

## نقاط مهمة لأي جلسة قادمة

- **حسابات متعددة بدون صلاحيات متدرجة (أدوار)**: كل مستخدم مسجّل يقدر يدير كل شيء (بما فيها إضافة/تعطيل/حذف مستخدمين آخرين، بس ما يقدر يعطّل أو يحذف حسابه هو نفسه وهو داخل فيه — حماية بسيطة من قفل النفس بره النظام). هذا قرار تبسيط متعمد (فريق صغير موثوق، مو شركة كبيرة) — لو طُلب لاحقًا فصل صلاحيات "مدير" عن "بائع"، يحتاج عمود `role` على `users` + فحوصات إضافية بكل route، مو بس بـ requireAuth.
- **رفع المرفقات آمن بتصميم**: `server/lib/upload.js` يستخدم قائمة mimetype مسموحة (JPG/PNG/WEBP/PDF فقط، مو امتداد الملف المُدخل من المستخدم)، اسم ملف عشوائي بالكامل على القرص (`crypto.randomBytes`، صفر اعتماد على اسم الملف الأصلي)، وحد حجم 10MB. التنزيل عبر `res.download()` يضبط `Content-Disposition: attachment` تلقائيًا فيمنع تنفيذ أي محتوى ضار كـ HTML/SVG مباشرة بالمتصفح. حذف عميل يحذف ملفاته فعليًا من القرص (مو بس صف قاعدة البيانات) عبر `fs.unlink` قبل `DELETE FROM customers`.
- **تحويل عميل محتمل لعميل**: `/customers/new?from_prospect=<id>` يعبّي نموذج البيع تلقائيًا (اسم/جوال/بائع/سيارة مهتم فيها) عبر حقل مخفي `from_prospect_id`، وبعد الحفظ الناجح `customers.js` يحدّث `prospects.stage='تحوّل لعميل'` و`converted_customer_id`. لو احتجت تغيّر ترتيب مراحل القمع، عدّل مصفوفة `STAGES` في `server/routes/prospects.js` فقط (مستخدمة بكل القوالب والفلاتر).
- **قائمة البائعين قابلة للتعديل من الواجهة** (`/settings`، جدول `salespeople`) بناءً على طلب صريح من المالك ("أقدر أتحكم بالموقع بدون ما أرجع لك"). عمدًا لم نجعل `PAYMENT_METHODS` أو `STATUSES` (في `customers.js`) قابلة للتعديل من الواجهة رغم تشابه الفكرة، لأنها مرتبطة بفئات رسمية معتمدة في برنامج جميل بلس (تبليغ المبيعات لازم يطابق فئات محددة) — لو المالك طلب جعلها قابلة للتعديل لاحقًا، وضّح له هذا القيد أولاً قبل التنفيذ.
- حذف بائع من `/settings` **لا يمسح** بيانات العملاء التاريخية المرتبطة بالاسم (الحقل `customers.salesperson` نص حر، مو مفتاح خارجي) — فقط يشيله من قائمة الاختيار لعمليات البيع الجديدة. `getSalespeople()` في `customers.js` تدمج جدول `salespeople` مع الأسماء التاريخية الموجودة فعليًا في `customers` (UNION) حتى تبقى ظاهرة في الفلاتر.
- **كتالوج السيارات** (`/cars`، جدول `car_inventory`، مفاتيح فريدة `UNIQUE(brand, model, year, trim, color)`) بنفس فلسفة قائمة البائعين: إدارة كاملة من الواجهة، وحذف عنصر لا يمسح بيانات البيع التاريخية. في نموذج إضافة/تعديل عميل (`views/customers/form.ejs`) القائمة كاملة تُمرَّر كـ JSON مضمّن في الصفحة (`CAR_INVENTORY`)، والفلترة المتسلسلة (شركة → موديل → سنة → **الفئة/trim** → لون) تصير بالكامل بجافاسكربت في المتصفح بدون أي طلبات AJAX إضافية — مناسب لحجم بيانات صغير مثل هذا. فيه خيار "كتابة يدوية" (checkbox يعطّل/يفعّل حقول الإدخال) للسيارات النادرة غير الموجودة بالكتالوج.
- **الهجرة (migration) لتركيبات قديمة**: `server/lib/schema.js` (`initSchema`، يشتغل على قاعدة بيانات كل معرض عند أول اتصال) يتحقق عبر `PRAGMA table_info(customers)` هل عمود `car_inventory_id` موجود، ولو لا يضيفه بـ `ALTER TABLE` — هذا يغطي أي نسخة سابقة من قاعدة البيانات أنشأها المستخدم قبل إضافة هذي الميزة، بدون ما يحتاج يمسح بياناته أو يشغّل أمر ترحيل يدوي. عمود `trim` أُضيف لاحقًا لجدول `car_inventory` عبر **إعادة بناء الجدول كامل** (rename → create → insert-select بنفس الـ ids → drop) بدل `ALTER TABLE ADD COLUMN` عادي، لأن قيد `UNIQUE` القديم كان يحتاج يتوسّع ليشمل `trim` وهذا مو ممكن بـ ALTER TABLE بسيط في SQLite. **درس مهم اكتشفناه بالاختبار الفعلي**: لازم تعمل `PRAGMA foreign_keys = OFF` قبل هذي العملية و`= ON` بعدها — لو تركتها مفعّلة، فإن `DROP TABLE` للجدول القديم يفعّل تلقائيًا إجراء `ON DELETE SET NULL` على كل صف في `customers` كان يشير له، حتى لو جدول جديد بنفس الاسم ونفس الـ ids صار موجود قبل الحذف. هذا سلوك SQLite موثّق (إجراء ترحيل الجداول الرسمي)، مو bug بالتطبيق — لكن لو نسيته، تفقد كل روابط `car_inventory_id` بصمت بدون أي رسالة خطأ.
- استعادة النسخة الاحتياطية (`POST /data/restore`) **تحذف كل البيانات الحالية وتستبدلها بالكامل** — هذا سلوك مقصود حسب الطلب، ومُحذَّر منه بوضوح في الواجهة.
- التصدير (`GET /data/export.csv`) يحترم نفس فلاتر صفحة العملاء (بحث/طرق دفع/بائع/شهر/حالة) عبر تمرير نفس query params.
- مجلد `data/` بالكامل (`registry.db` + `tenants/*`) وملف `.env` غير مرفوعين على git (`.gitignore` يستثني `data/tenants/` و`data/registry.db*` صراحة، مو بس أنماط `data/*.db` السطحية التي لا تغطي المسارات المتداخلة) — أي جلسة جديدة تحتاج `cp .env.example .env` قبل التشغيل.
- لا يوجد اختبارات آلية (unit/e2e) — تم التحقق يدويًا عبر curl + Playwright screenshots أثناء البناء (راجع سجل المحادثة إن احتجت إعادة الفحص).

npm install                    # تثبيت المكتبات (مرة واحدة)
